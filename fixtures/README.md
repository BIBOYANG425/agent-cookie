# Sample demo seed

These are synthetic **Sample** records, not a real person's identity. Live UCP captures live separately in `ucp/` with their own provenance.

| File | Contents |
| --- | --- |
| `users.json` | One stable `userId`, `sample-user`, Sample name and explicitly public demo derivation secret. |
| `agents.json` | Two personal agents, ACME (`category: shoe`, `chatEndpoint`) and `Sample · Assistant` (`sample-assistant`, `category: assistant`, no endpoint), a Sample company assistant for the bring-your-own-agent demo. |
| `contributions.json` | Exactly three personal `stated` records: `lang=zh`, `tone=简短`, `shoe_size=42`. |
| `address.json` | One Sample `shipping_address` field/value; the workspace and memory seed derive the same fourth contribution from it. It is not a valid shipping destination. |
| `dev-keys.json` | Five public Sample keys bound to the two personal agents, owner, ACME and the Sample assistant (`ck_assistant_sample`, role `assistant`). Only demo/test mode may load them. |
| `memory/` | Generated initial Git memory content: three explicit contributions plus one derived Sample address, a medium-confidence card, contract policy in YAML, a short `MEMORY.md` index, and empty notes/receipts/archive. |

Field names follow the merged `@agent-cookie/contract` SeedUser / DevKeys definitions. Categories are `personal | shoe | retail | assistant`; these registered Sample agents use personal/shoe/assistant, while UCP store proxies use retail. `node fixtures/verify.mjs` checks the explicit JSON fixture shape and cross-file bindings without printing keys or secrets. The memory-policy test separately fails if the committed seed differs from the current contract's `POLICY_TABLE`, including retail and its learned-preference fields and the assistant category, and pins the policy id the seed reads as.

The personal `stated` exception is why these three single-source records can eventually appear on the card with medium confidence. They do not demonstrate two independent merchant observations; A02 must create those through HTTP. The console's current preview uses the separate `console/generalized.json` presentation fixture and `learning/console.json` scripted learning stages; it does not implement merging or change this workspace seed.

The second personal agent supports A22. The single SeedUser and its fixed Sample secret are restored by demo reset, so both personal agents refer to the same user and stable merchant IDs remain stable. `dev-keys.json` is deliberately public Sample data, loaded by A's importer only with `AGENT_COOKIE_DEMO=1` or `AGENT_COOKIE_TEST=1`; real keys are minted by the workspace and must not enter fixtures. `contributions.json` stays at three explicit records. Following the workspace's `loadFixtures`, the memory generator derives `seed-shipping-address-01` from `address.json`, attributed to the first personal agent, dated one second after the newest explicit contribution. The generated card includes that same Sample address so reset does not need a repair write after restoring the initial commit.

The Sample assistant is demo data only: it stands in for a company-built assistant so the console's 连接请求 panel and the assistant routes can be exercised with `AGENT_COOKIE_DEMO=1`. Its key lets it ask for a consent link, nothing more. No link, session or grant for it is seeded, and none may be added here: a link only ever exists because the assistant asked (`POST /assistant/link`) and the owner approved it (console, CLI or gateway). `verify.mjs` checks there is exactly one assistant, its key binding, and that no `links.json` exists. The policy's assistant floor (never `shipping_address` or `payment_method`) is the contract's, not this fixture's.

ACME's endpoint is validated against the upstream source before Tier 0 is enabled. The workspace alone renders policy-approved auto values into its first text message; this fixture does not contain a handshake or render a prefix. Sample addresses must never be sent to a real cart/checkout.

`packages/rules/scripts/generate-seed.ts` generates `memory/CARD.md` with the real rules and a deterministic date at least as recent as every seed contribution. With the formal contract and workspace dependencies installed, run it from the repository root using `pnpm exec tsx packages/rules/scripts/generate-seed.ts`. It emits block-style `POLICY.yaml` directly from the installed contract; no second policy table is maintained. After a contract change, regenerate before running the seed consistency test. For an isolated contract overlay, regenerate only that temporary copy's seed. Do not hand-edit the generated card or policy. `@agent-cookie/memory-repo` copies this directory into one tagged `fixtures-seed` commit; its lifecycle tests load this actual seed, regenerate the card, and reset to the seed bytes.

`MEMORY.md` is one introductory line followed by a root-relative wikilink index to the card, contribution file, receipts, policy and archive README. Each contribution remains one physical bullet line. Existing metadata keys remain; new records add `added` as the UTC date of `at`, plus `source: conversation/<id>` when a conversation is known, otherwise `source: intent/<id>`. If both identifiers exist, conversation is the display source and both original ID attributes remain. These prefixes are local provenance references, not URLs or permission grants. Imported `added`/`source` values and open keys such as `custom_key`, `custom-key`, `archivedAt` and `from` survive parsing and rendering without becoming contribution/owner fields. Writers that clone parsed records must preserve property descriptors so this non-enumerable metadata survives revocation; it stays out of JSON/API projections.
